# 0015 — Grounded workflows: multi-step tool runs that cannot invent facts

- Status: Proposed (2026-10-21). Requested by the owner: "an agentic workflow of, let's say, I tell him to search my flight, it goes and does the web search, returns me the tickets, and ensures it is not hallucinating", with explanations condensed to one line. Built on `awais/agentic-workspace`; needs the owner's review.
- Related: [0007 model routing](0007-model-routing.md), [0006 spend guard](0006-global-spend-guard.md), [0013 AI layer](0013-ai-layer-integration-and-local-simulation.md), [PROVIDER-RELIABILITY.md](../PROVIDER-RELIABILITY.md), [0016 Google connectors](0016-google-connectors.md).

## Why

The tool loop (decision 0013) lets the model call `web_search` and answer with `[n]` citations. That is not enough for a request like "find me a flight from London to New York on 12 November": one search returns five short excerpts, the model has nothing to check its numbers against, and research in October 2026 still measures about 30% hallucination for the best searched models and 3-13% invented citation URLs. The owner wants the assistant to run a workflow (plan, search several times, read the pages, extract, verify, answer) and to show what it did as one line per step.

What was checked before this design (2026-10-21): Nebius Token Factory has no built-in web search; Nebius bought Tavily (announced 2026-02-10, closed 2026-02-19) but Tavily stays a separate API with its own key and credits. Tavily's `search` (1 credit basic, 2 advanced) finds fare and schedule pages, and `extract` (1 credit per 5 pages) reads route and airline pages such as `kayak.com/flight-routes/...`, `momondo.com/flights/...`, airline "flights from X to Y" pages and Google Flights SEO pages; live search-result pages of Kayak, Skyscanner and airlines come back as empty shells and their terms forbid scraping. No self-serve flight API with a free tier remains (Amadeus Self-Service closed in July 2026, Kiwi Tequila is invitation-only, Skyscanner and KAYAK are partner-only). So a v1 on Tavily can give verified "fares seen on this page on this date" and hand-off links, not bookable live fares.

## Decision

### A workflow is a tool with steps

A workflow runs inside one tool call of the existing loop. The model calls it like any tool, the service runs the steps, and the tool result goes back to the model inside delimiters as data. No new hop limit is needed: a workflow tool call is hop 0 and the answer is hop 1.

Module: `src/server/assistant/workflows/` with one file per workflow and a shared core:

- `core.ts`: `runGroundedLookup(ctx, plan)` runs the search queries (at most 3, in parallel, each reserving its Tavily credits first), dedupes URLs, keeps results with `score >= 0.5`, extracts at most 5 pages with one `extract` call (1 credit, `basic` depth, `query` and `chunks_per_source: 3`), numbers every page as a source, then calls the extraction model once with a forced tool call (`tool_choice: {type: "function", ...}` through the executor, on the `fast` tier, with its own hold through `attemptBudget`) and verifies every item it returns. A step reporter emits one `step` event per stage.
- `verify.ts`: pure functions. An item is kept only when (1) its `quote` is a verbatim substring of the numbered source's extracted text after whitespace normalisation, (2) every number the item states (price, times) appears inside the quote, and (3) its named entity (airline, product) appears in the quote. Everything else is dropped and counted. The model never sees unverified items as facts.
- `flights.ts`: the `search_flights` tool. Arguments: `origin`, `destination`, `depart_date` (ISO date, today or later), optional `return_date`, `passengers` (1-9). Queries: "flights from {origin} to {destination} {date} price" and "{origin} to {destination} flights schedule nonstop airlines", the first with `include_domains` in `prefer` mode for the pages Tavily can read (kayak.com/flight-routes, momondo.com/flights, expedia.com/lp/flights, aa.com, united.com, delta.com, britishairways.com, virginatlantic.com, google.com/travel/flights). Extraction schema: `options[]` of `{airline, route, departs, arrives, stops, price, currency, quote, source}`. Output for the model: a `<flight_results>` block listing only verified options with their source number, the page's own "seen" date when the quote has one, the number of dropped candidates, and three hand-off links (Google Flights, Kayak, Skyscanner deep links built from the arguments; they are links for the user, never fetched). The model is told that fares are snapshots and must be confirmed on the link.
- `research.ts`: the `verified_research` tool for any other multi-source question: the same core with a claims schema `{claim, quote, source}`. Verified claims go back as `<research_results>`; the count of dropped claims is stated.

### What the user sees

- `step` events: `{type: "step", id, label, status: "running" | "done" | "failed", detail?}`. One line each, in the form "verb + object + count": "Searched the web for LHR to JFK on 12 Nov · 9 results", "Read 4 pages", "Verified 3 of 5 fares", "Answering". The chat shows them in a run panel with a one-line header ("Worked for 14 s · 4 steps · 4 sources") that is open while streaming and collapsed when the reply is done. The existing `thought` event becomes a step.
- `results` events: `{type: "results", kind: "flights", summary, items[], dropped, links[], sources[]}` rendered as cards above the reply: airline, route, times, price with currency, "Seen on <date>" when known, the source link, and a "Verified from source" badge. A reply with no verified item shows the hand-off links and the one line "No fare could be verified from the pages read."
- Persistence: a new table `message_results` (`message_id` primary key with a foreign key `(message_id, user_id)` to `messages`, `user_id`, `kind`, `payload jsonb` up to 32 KB, `created_at`), RLS select and insert own, no update, migration `20261022000500_message_results.sql`, written with `waitUntil` after the reply is saved, like context records. `GET /api/messages/:id/results` returns it; the card loads it lazily when a conversation is reopened. The text reply keeps its `[n]` citations, so history reads correctly even without the card.

### Cost and limits

- Every search reserves its credits first (`tavilySearchCredits(depth)` and `tavilyExtractCredits(pages, depth)` in `src/server/assistant/spend.ts`, the only owner of credit prices); a refusal ends the workflow with "search limit reached" as its result. A flight search costs 2 search credits + 1 extract credit. The per-user daily default (10 credits) allows three flight searches a day; the owner can raise `TAVILY_USER_DAILY_CREDITS` up to the SQL cap of 20.
- The extraction call is one `fast`-tier call with a hold computed by `nebiusHoldMicroUsd` over its own messages; the extracted text sent to it is capped (5 pages × 3 chunks × 800 characters). The final answer is the normal next hop.
- Wall clock: searches run in parallel (Workers allow 6 outbound connections), extract has a 30 s timeout, the model call has the fast tier's deadline. `signal` is checked between steps; Stop settles every hold.
- Tavily requests send `include_usage: true` and the step detail logs credits as metadata, never the query text.

### Rules

- A number, time or name the user sees as a result was copied from a page the workflow read, and the quote that supports it is stored with it. Anything the verifier drops is counted, never shown as a fact.
- Retrieved pages are untrusted data: delimited, neutralised, size-capped, and never instructions.
- Deep links are built from the user's own arguments and labelled "check live fares"; the app never claims a price is bookable.
- The workflow never books, pays or changes an outside account.

## Amendments after review (2026-10-21)

Three critics (security, repository rules, product) reviewed this decision. These changes replace the parts above where they differ.

### Code owns the facts (flights)

- The extraction model returns **spans**, not values: `{airline_text, price_text, departs_text?, arrives_text?, stops_text?, quote, source}`. Every span must be a verbatim substring of `quote`, and `quote` (at most 240 characters) must be a verbatim substring of **one** extracted chunk of the numbered source; a quote that matches only across two chunks is dropped.
- Code parses `price_text` into an amount and a symbol. An ISO currency is set only when the quote has an ISO code or an unambiguous symbol (£, €, ¥ with context, US$, C$, A$); a bare `$` is shown as written with "currency not stated". Code derives the price basis from the quote: per person, round trip, one way, "from", or a range (`$441–1,585` is kind `range`, never a single fare). Prices are never multiplied by passengers.
- Numbers match on token boundaries after normalising thousands and decimal separators (`412` does not match `1,412`). A quote with more than one price token or more than one airline name is dropped as `ambiguous_quote`.
- **Route and direction:** `src/server/assistant/workflows/airports.ts` holds an alias table (IATA code, airport names, city names) for the most-flown airports. Both the origin and the destination must appear in the quote or in the heading of its chunk, origin first or in a "from X to Y" / "X–Y" pattern; otherwise the item is dropped as `wrong_direction` or `route_not_stated`.
- **Date:** an item is a *fare for your date* only when the quote contains the departure date in a parseable form (12 Nov, 2026-11-12, Wed 12 November). Other verified items go to a separate list, **Typical prices on this route**, labelled with the page's own phrase ("cheapest in the last 72 hours").
- Every drop has a reason (`quote_not_found`, `price_not_in_quote`, `airline_not_in_quote`, `wrong_direction`, `route_not_stated`, `ambiguous_quote`, `cross_chunk`), counted separately.
- **The reply is checked too.** Code writes the first line of the saved reply from the verified items ("3 fares quoted on 2 pages for Wed 12 Nov 2026; lowest quoted £412 on britishairways.com. Confirm on the links."), so history reads correctly without the card. `checkReplyClaims(reply, verified)` finds every currency amount and clock time in the model's text; any not in the verified set is stored with the result as `unverifiedMentions`, and the card says so. A refused or empty run tells the model: "No fare was read; do not state any price, time or airline as current."
- **Flight intent forces the tool.** The router detects a flight request (flight, fly, fares, tickets plus a place or a date) and hop 0 is sent with `tool_choice` naming `search_flights`. The toggle search is skipped for that turn, so unverified excerpts never reach the answer.
- **Dates in the user's time zone.** `POST /api/chat` takes an optional IANA `timeZone`; the prompt states the local date and weekday; `depart_date` must be from local today to 330 days ahead. A city the alias table cannot resolve, or one with several airports, returns one clarifying question and reserves no credit.
- **Sources:** prefer rome2rio.com, airline "flights from X to Y" pages, Google Flights SEO route pages and en.wikipedia.org route tables; KAYAK, momondo and Skyscanner are excluded from extraction (their terms forbid automated access). Hand-off links: Google Flights (`?q=`) and Skyscanner only, built with `new URL` and `URLSearchParams`, IATA codes in paths only when they match `^[A-Z]{3}$`, hosts checked against an allow list, formats pinned by tests.
- **Cards:** the list is titled "Fares quoted on travel pages", above it a code-built trip line ("London (LHR) to New York (JFK) · one way · Wed 12 Nov 2026 · 1 adult"). Each card shows the price as written plus basis chips, only the fields that were verified ("not stated on page" otherwise), the badge **Quoted from <domain>** with the quote in a popover, "Read 21 Oct, 14:05" (fetch time) apart from the page's own freshness phrase, and, after 6 hours, "Read 3 days ago · fares change" with a Re-check button.

### Research

- `verified_research` shows the verbatim quote as the fact and the model's claim only as its label; a claim that is not close to its quote is marked "paraphrased". Claims whose quote addresses the assistant ("ignore previous", "you must", "system prompt", "P-Dot") are dropped. The block header says that "verified" means only that the text is on the page, and that it is still untrusted.

### Streaming, limits and safety

- **Tool-only streams count as a first token.** The Nebius client yields a text-less progress chunk when a tool call starts arriving, so the executor's first-token timer and hedge do not misfire on a forced tool call. The extraction runs on its own plan (from the `standard` tier, hedge off, 2,048 output tokens, at most 8 items); `finish_reason: length` or a parse failure is a failed step ("Could not read the results"), never "0 verified".
- **Live steps.** `runTool` becomes an async generator, so a workflow yields `step` events while it runs. Steps have the status `partial` with drop reasons ("Verified 3 of 5 · 2 dropped: wrong date"). Step labels are streamed and stored, never logged; logs get step IDs, statuses, counts and credits only.
- **Old tabs keep working.** `readChatStream` skips unknown event types instead of failing; the server keeps sending `thought` alongside `step` for one release.
- **Credits:** all of a workflow's Tavily credits are reserved, one reservation per call (at most 2 credits each, as the SQL requires), before any Tavily call. If one is refused, the granted ones settle to 0 and the step says "search limit reached". A flight run costs 2 search + 1 extract credits; research up to 4. `tavilySearchCredits` and `tavilyExtractCredits` live in `spend.ts` and throw above 2 credits or 5 URLs.
- **One workflow per reply,** and no workflow tools on the hop after one. Every tool result has a byte cap, and before a tool runs the service checks that the next hop's worst-case hold still fits under the ceiling; otherwise the tool answers "not run: context full" without calling Tavily or Google.
- **Tainted replies.** Once a hop returns `<flight_results>`, `<research_results>` or `<connector_results>`, later hops of that reply offer no tool that sends text outside P-Dot (`web_search`, `search_flights`, `verified_research`) and no connector tool, and the `done` event tells the browser that Auto may not run anything for that reply.
- **Encoding.** Every untrusted field in the new blocks (titles, quotes, page text, file names, event titles) has `<` and `>` replaced with `‹` and `›`, and the new tag names join `neutralize()` and the untrusted-block sentence of the system prompt.
- **Persistence:** `message_results` has `on delete cascade` to `messages`, `kind in ('flights','research','calendar','drive')`, a 32 KB check, and a payload `{results, steps}` so the run panel and its audit trail survive a reload. Conversation detail returns each message's results; the payload is parsed with a strict schema on read and never sent back into a prompt. Code that reads `message_results` treats a missing table (the migration not applied yet) as "no results".
- **Local runs:** Ollama ignores `tool_choice`, so a text reply to the extraction counts as a failed step; `docs/LOCAL-SIMULATION.md` documents `OLLAMA_CONTEXT_LENGTH=16384`. `TAVILY_KEYLESS=true` (development only, never on the deploy allow list) lets a local run use Tavily's keyless access.

### Changes after the final review and a local run (2026-10-22)

- **Code parses a clear flight request.** A local model ignored the forced `tool_choice` and answered in text, and forcing the tool on a vague request ("cheap flights to Lisbon") made a model invent the missing origin and date. So `parseFlightRequest` (in `workflows/request.ts`) reads the origin, destination, date, return date and travellers from the user's own words. When all three required parts are there, the service runs the flight check itself before the first model call, and the model only writes the answer from the verified results. When a part is missing, nothing is forced: `search_flights` is offered normally, and it refuses without spending credits unless the origin, destination and date appear in the user's latest or previous message, so the model asks instead of guessing.
- **A reply that talks about fares without a check is marked.** When a flight request ends without a flight check and the reply contains an amount or a time, the run panel shows the failed step "Not verified: no travel page was read for this reply".
- **Connector reads may follow a connector read** in the same reply (a Drive search, then reading the file it found), because they send nothing outside Google and P-Dot. Web search, flight checks and research stay blocked after any workflow or connector result, connector reads stay blocked after a workflow result, and Auto still runs nothing for that reply.
- **An oversized result is trimmed, not dropped.** Step details, long calendar and Drive lists and extra quotes are cut until the payload fits 32 KB; the flights summary and its unverified mentions are always kept. A trimmed payload carries `trimmed: true`, so "What was sent" says "at least N".
- **Code reads a flight request only when it is clear.** It returns nothing (and the model asks) when children are mentioned, a group has no count, there are more than 9 travellers, a count or stay length sits next to a month, a date is a range or approximate, a return is asked for without a return date, or a destination is followed by a name the table does not know. `search_flights` checks the origin, destination, departure and return dates against the latest and the previous user message, read separately; lower-case three-letter words that are also airport codes ("can", "was", "per") do not count as places.
- **More verifier rules:** space- and apostrophe-grouped thousands (1 412 €, CHF 1'412) are one number; a claim whose negation differs from its quote is marked paraphrased; a quote naming a second carrier, listed or not, is dropped as `ambiguous_quote`; a page's "updated", "checked", "found" or "seen" date never counts as the departure date; the reply check also reads hours like "6pm".
- **The room check covers every tool** (web, document and memory searches too), and connector blocks are cut by UTF-8 bytes to their cap.

## Open decisions

- Whether the reply check should also tie each verified amount to its airline, date and list (today it checks only that the amount and time appear among the verified ones).
- Passenger counts the model passes to `search_flights` are not checked against the user's words (places and dates are).
- A flight-data connector (v2): SerpApi `google_flights` (250 free searches a month, scrapes Google Flights, terms risk) or Duffel (bookable offers with `expires_at`, needs a business account) would give structured fares. Record the owner's choice before building it.
- Currency: v1 keeps the currency as written on the page and validates only that one appears in the quote; a "show in my currency" setting needs a rate source.
- Whether `verified_research` should replace plain `web_search` for every search-toggle request (3 credits instead of 1).
- `response_format: json_schema` on Token Factory is documented in the guide but contradicted by the request schema, and no Nemotron model carries the JSON-mode tag; the forced tool call is used instead and should be measured on `nvidia/Nemotron-3_5-Lightning` with the eval runner before public launch.
